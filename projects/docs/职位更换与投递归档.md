# 更换投递职位

HR 可在候选人详情顶部点击“更换投递职位”。更换时需选择不同职位并确认；可填写原因。

- 新投递使用新的记录 ID，从新职位流程的“新简历”（没有时使用“待筛选”）开始，重新筛选。
- 原投递不覆盖、不删除，系统归档为 `job_changed / closed`。原阶段保存在 `archived_from_stage`，并记录归档原因和阶段流转。
- 新投递不继承原职位的匹配结果、业务复筛人、面试评价、审批结果或薪资安排。
- 原投递尚未完成的面试取消、待审批任务取消、未完成的 Offer 撤回、未完成的入职办理取消；已完成的面试、评价、审批步骤等历史内容保留。
- 新旧投递分别通过 `previous_application_id`、`replacement_application_id` 关联，可通过投递下拉框和投递分析查看。
- 阶段人数、流程看板和待安排面试不把更换后归档的原投递作为当前流程。
- 只能由有权限的负责 HR 或超级管理员操作；保留版本检查、候选人锁定和并发保护。
- 重复提交、无效职位、已有目标职位进行中投递等情况会拒绝处理；失败时事务回滚或单机补偿恢复原投递和锁定。

## 面试安排入口

编辑面试时更换职位，需额外确认。确认后仅更换投递并重新筛选，不创建新职位面试；后续由 HR 在新投递中重新推进。

## 接口

`POST /api/candidates/{candidate_id}/change-job`

```json
{
  "application_id": 123,
  "version": 1,
  "job_id": 456,
  "reason": "更适合另一个岗位"
}
```

返回新投递记录。原投递仍可查询，但不能继续流转或审批。

## 验证

`backend/tests/test_job_change.py` 覆盖筛选、业务复筛、各面试轮次、审批、待入职更换职位，历史留存、阶段统计、权限、版本冲突、回滚和并发。

本地后端需要重启以加载新路由；前端开发服务可通过热更新加载界面修改。不需要覆盖或迁移现有业务数据。
